# 수동 모의 체결의 자동 관리 연결

사용자가 직접 요청한 원장에 기록된 수동 매수의 미청산 전량을 기존 일봉 전략으로 편입한다. 원주문이 없는 외부 잔고, 다른 계좌·실계좌·미체결·부분 체결은 자동 편입하지 않는다. 원격 전체 주문·잔고·매도가능 수량을 같은 프로세스에서 최신 대조한 뒤만 연결한다.

Code/trading/strategy_adoption.py의 adopt_manual_fill이 관리 주체와 보호선 메타데이터를 같은 SQLite 주문 원장에 저장한다. 원주문 ID·증권사 접수번호·수량·체결금액·날짜·상태는 바꾸지 않는다. 기존 수동 소유자와 원주문 전체 사본을 management_adoptions 영수증에 보존하며 신규 매수 신호·가상 체결을 만들지 않는다. 비용·현금 위험 승인을 주지 않는다.

보호선은 실제 누적 체결 평균가-2.5ATR, 관리 시작 시 확인한 고점-3.5ATR, 원주문의 기존 손절가 중 가장 높은 값을 사용한다. ATR은 관리 편입 시점에 이미 확정된 최신 일봉으로 계산한다. 미관측 장중 고점을 만들지 않는다. 원주문 날짜를 보유 시작 거래일로 사용하며 개별 체결 시각을 안다고 표현하지 않는다. 기존 비용 대기·매수 중지는 유지하고 실제 확인된 자기 보유의 매도 경로만 기존 축소 검사로 관리한다.

이미 확정된20일 저점 이탈 또는126거래일 보유 조건이 있으면 매도 계획도 이어받는다. 권위 원장에 편입 영수증이 저장된 뒤 계좌 투영 저장이 실패해도 다음 전체 대조에서 복원된다. 동일 연결은 중복 체결·계획을 만들지 않는다. 청산된 보유를 다시 만드는 재실행은 거절한다.

운영 연결은 해당 계좌 프로세스를 정상 종료해 단일 원장 잠금을 확보하고 SQLite backup API와 계좌 백업을 만든 뒤 수행한다. 기존 StrategyDemoPort.refresh를 강제해 전체 계좌를 새로 대조하고, 편입 뒤 다시 조회·sync해 실제 보유 수량과 보호선이 전략 계좌에 나타나는지 확인한다. 읽기 전용 단계에서는 금융 HTTP를 차단한다. 재개 후 매도 조건 충족 시 기존 KIS 모의 지정가 경로에서 매도될 수 있다. 실계좌·차입 매도·새 매수는 허용하지 않는다.

후속 운영은 기존 사용자가 켠 당일 실행 종료 시각까지다. 부팅 자동 시작을 켜거나 무기한 서비스를 새로 등록하지 않는다. 종료 중에는 서버에 상시 손절 주문이 걸려 있는 것으로 해석하면 안 된다. 사용자가 켠 실행이 시세를 관측할 때 보호 매도를 판단하는 구조다.

CMD 검사: 프로젝트 루트에서 `python Code/main.py --test all`. 실제 편입·현재 보호선·운영 반영 근거는 Data/reports/position-adoption의 최신 보고서를 따른다. 함수 호출만으로 실제 매도 체결을 검증했다고 표시하지 않는다.


## 재사용 수동 편입 메뉴와 로컬 API

설치 루트에서 `python Code/manage_positions.py`를 실행한다. Pi는 `.venv/bin/python Code/manage_positions.py`다. 메뉴는 원장 조회만 하며 자동으로 주문하거나 보유를 이전하지 않는다. 원하는 종목 번호를 고른 뒤 `편입`을 입력하면 신청 파일을 만든다. 실행 중인 기존 일봉 전략이 다음 해당 종목의 정규장 관측에서 실제 계좌를 대조하고 처리한다. 프로세스를 강제로 중지할 필요가 없다. 처리 상태는 같은 메뉴의 신청 목록에서 확인한다.

CMD에서 Pi 메뉴를 열려면 `ssh -t pytrading-pi "cd /opt/PyTrading && .venv/bin/python Code/manage_positions.py"`를 사용한다. Windows 로컬에서 만든 신청은 Pi로 자동 동기화되지 않는다. 기존 실행 메타데이터가 있으면 해당 모의 설정/계좌를 사용하고, 없으면 선택된 kis_demo 설정과 기본 일봉 계좌가 먼저 준비돼 있어야 한다. 실계좌·내부 모의는 이 메뉴의 편입 대상이 아니다.

로컬 Python API는 trading.adoption_requests.list_positions(), request_adoption(), apply_pending_requests()다. 원격 HTTP 서버·새 주문 API가 아니다. 목록은 로컬 장부의 신청 가능 여부이며 실제 잔고 검증 완료 표시가 아니다. apply_pending_requests는 일반 사용자가 직접 참/거짓을 주는 함수가 아니라 기존 StrategyDemoPort.sync가 현재 프로세스의 실제 전체 조회 뒤 호출한다.

신청은 Data/management/adoption-requests/<신청ID>.json에 저장한다. 계좌 지문·모의 환경·대상 전략·체결 계약 해시·설정/후보 버전·사용자 신청 시각을 묶는다. 24시간 안의 신청만 처리하며 모드·계좌·체결·후보가 달라지면 차단한다. QUEUED → PROCESSING → APPLIED 또는 FAILED/EXPIRED를 남긴다. 실제 처리 전에 최신 호가·전체 주문·잔고·매도가능 수량을 다시 검사한다. 저장 장애·재시작 때 같은 신청을 두 번 편입하지 않는다.

수량은 선택한 원주문의 전량 체결분이다. 1주에 고정하지 않지만 임의 수량을 넣거나 다른 잔여 보유를 배분하지 않는다. 같은 종목의 청산 완료 과거 거래는 허용한다. 같은 날 체결된 보유는 그 전일까지 확정된 ATR로 보호선을 계산하며, 매수 이전 날의 매도 신호를 소급 적용하지 않는다. 이미 연결된 보유는 '관리 중'으로 표시하고 중복 신청하지 않는다.

현재 지원하는 원주문 소유자 이름은 user_requested_single_demo 또는 manual_user다. 증권사 앱에서 매수했지만 프로그램 원장에 없는 외부 보유는 자동으로 가져오지 않는다. 해당 매수의 정식 주문/체결 대조·등록 경로가 먼저 필요하며, 누락된 체결·원가를 임의 입력하지 않는다. 부분 체결·일부 청산 후 원가 배분, 다른 전략의 잔여 수량이 겹친 종목도 검토가 필요하다. 신규 매수의201봉 준비 조건과55일 돌파 규칙은 이 수동 관리 메뉴를 추가하면서 바꾸지 않았다.

이 문서의 장비 이름, 사용자명 및 절대 경로는 공개용 예시다. 실제 환경에서는 로컬 값을 사용한다.
