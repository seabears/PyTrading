# 실적 데이터 신뢰성·수익성 검증을 위한 수집 계획

## 현재 확인한 범위

2026-10-25에 관찰 30종목의 SEC CIK·티커·회사 이름과 원본 접근을 대조했다. 이는 30종목 모든 실적 수치를 대조했다는 의미가 아니다. Apple·Microsoft·Nvidia의 9개 발표에서 매출·GAAP EPS 18항목을 비교해 14항목 일치, 분기 단독 SEC 사실이 없는 4항목은 미검증으로 남겼다. 조정 EPS는 별도 조정표 검증이 필요하다.

실제 발견한 문제: Microsoft FY26Q2의 'GAAP 기준 EPS' 문구를 놓쳐 뒤쪽 주석 금액을 읽은 추출 오류를 SEC 대조가 검출했다. 발표 본문 범위와 회계 기준 문장을 명시적으로 읽도록 수정하고 테스트했다. 회사 원문 자체의 오류로 판정한 것이 아니다.

## 필요한 데이터와 저장 항목

|데이터|필수 항목|수집·검사 방법|
|---|---|---|
|회사 식별|티커·거래소·CIK·회사명|SEC 공식 티커표와 submissions, 기존 종목 이름 대조|
|실제 실적|분기 시작/종료·매출·희석 EPS·통화·단위·GAAP/조정 기준|SEC XBRL 원본과 회사 IR 원문 대조, 조정 EPS는 조정표 별도 확인|
|시장 예상치|같은 기간·기준의 EPS/매출 예상·제공자·발표 전 수신 시각|예상치 제공 API를 발표 전에 조회해 변경 불가능한 원본 파일로 보존|
|발표 시각|시간대 포함 실제 공개·SEC 접수·시스템 최초 수신·검증 완료 시각|수신 시각은 로컬 UTC 시계로 별도 저장, 날짜만 있으면 당일 시가 진입 금지|
|가이던스|동일 대상 기간의 기존/새 전망·원문·변경 시각|전 분기 전망과 다음 분기 전망을 단순 비교하지 않음|
|시세·체결|분봉·호가·거래량·거래소 정규장·가정 비용|기존 KIS 수집 자료와 실제 알 수 있게 된 시각 이후로 연결|
|정정·감사 이력|원문 URL·SHA256·접수번호·조회 시각·추출 버전|원본을 덮어쓰지 않고 버전별 보존. 정정은 이후 인지 시점부터 반영|

## 출처별 역할

- [SEC 공식 API](https://www.sec.gov/search-filings/edgar-application-programming-interfaces): 인증 키 없이 실제 제출 실적·회사 식별을 확인할 수 있다. 회사 공시의 실제 실적이며 시장 예상치 제공 API로 간주하지 않는다.
- [회사 IR](https://www.microsoft.com/en-us/investor/earnings/fy-2026-q2/press-release-webcast): 발표 원문·회계 기준·조정표 확인. 회사가 발표한 실제 수치와 애널리스트 예상치를 구분한다.
- [Alpha Vantage 공식 문서](https://www.alphavantage.co/documentation/): EARNINGS는 분기 EPS·애널리스트 예상·surprise 항목을 제공한다고 안내한다. 조회한 과거 값이 당시 저장된 빈티지인지, GAAP/조정 기준이 무엇인지 별도로 확인해야 한다.
- FMP는 사용자 요청으로 사용 대상에서 제외했다. 키 발급·운영 연결·수집을 진행하지 않는다.

현재 사용 중인 예상치 서비스가 없으므로 예상치 API를 운영 연결하지 않았다. 서비스를 정할 때는 이용 범위·호출 한도·과거 빈티지·GAAP/조정 기준·통화·정정 정책을 확인해야 한다. 현재 코드의 검증 소스 허용 목록은 별도 정책이며 위 후보 API가 자동 허용·구현된 것은 아니다.

## 수집 순서

1. 현재 30종목 중 실제 발표 일정이 확인되는 종목부터 시작한다. 발표 예정일 변경도 시각과 함께 저장한다.
2. 발표 전 매일 예상치를 저장하고, 발표가 가까워진 종목은 제공자의 허용 주기 안에서 더 자주 저장한다. 파일마다 원문 응답·실제 수신 UTC·SHA256을 남긴다. 기준·통화를 제공하지 않으면 unknown으로 남겨 매매용으로 통과시키지 않는다.
3. 발표가 나오면 IR/SEC를 별도로 수집한다. 표준 XBRL의 연간·누적 값으로 분기 EPS를 만들지 않는다. 제공자의 조정 EPS는 회사의 같은 조정 기준과 대조해야 한다.
4. 회사·기간·통화·회계 기준·실제 수치·발표 전 예상치 원본·발표/수신/검증 시각을 모두 확인한 사건만 검증 목록에 등록한다. 단순 confirmed=true 플래그로 통과시키지 않는다.
5. 검증 완료 시각 이후의 정규장 시세에서 기존 가격·거래량 규칙을 모의 재생한다. 시간 자료가 없는 과거 기사에 수신 시각을 만들어 붙이지 않는다.
6. 1차 연구 기준은 최소 10기업·30발표와 서로 다른 기간으로 삼되, 통과 자체를 수익성 보증으로 보지 않는다. 같은 자금의 뉴스 미사용 전략·현금·시장 지수와 비용 두 배 조건을 함께 비교하고, 새 자료 구간은 조건 조정에 사용하지 않는다.

## 현재 프로그램 동작

`Config/earnings.json`의 `require_primary_verification=true`가 기본이다. 증거 없는 제목 신호는 모의 매수와 뉴스 기반 매도를 발생시키지 않는다. `earnings_awaiting_verification`은 해당 근거가 부족하다는 뜻이다. 가격 손절·추적 보호·보유 관리는 계속 검사한다. 실행 중인 프로그램은 재시작해야 적용된다.

`Data/earnings-audit/verified-events.json`은 현재 비어 있다. 회사 실적 수치가 맞더라도 발표 전 예상치 증거까지 갖춘 사건이 없기 때문이다. 검증기가 요구하는 증거에는 SEC 원본·submissions·발표 전 예상치 JSON과 각 해시, 회사·기간·단위·기준·수신 시각이 포함된다. GAAP EPS 비교만 지원하며 조정 EPS나 가이던스는 검증 완료로 추정하지 않는다.

`python Code/main.py --test earnings-audit`: 저장된 공식 원문을 다시 대조하고 별도 가격 진단 보고서를 만든다.
`python Code/main.py --test unit-earnings`: 분류·원문 기준·미검증 매매 차단 검증.

## 수익성 검증의 현재 상태

실제 시스템의 과거 실적 수신 이력과 발표 전 예상치 스냅샷이 없어 원래 실적 호재/악재 전략의 수익성은 판정할 수 없다. 공식 발표 7건의 원본 수치 확인일 이후 단순 보유를 별도로 진단했으며, 이는 원래 전략의 백테스트나 계좌 수익이 아니다. 오늘 원문을 조회한 것을 과거 인지 기록으로 취급하지 않았다.
