# 전략 모의계좌의 체결 후 정산

2026-11-03 개발. 실제 주문·실계좌 실행·운영 서비스 자동 시작을 허가하는 문서가 아니다.

## 구현한 흐름

기존 전략 → 영속 주문 의도 → KIS 모의 접수 → 전체 주문/보유 대조 → 비용 대기 → 검산 가능한 확정 정산 → 손익·위험 재평가 → 다음 신규 주문 전 전체 계좌 재대조 순서다. 이 개발에서는 실제 주문을 전송하지 않는다.

- `trading/strategy_posttrade.py`: 현재 계좌의 정규화 원본을 기존 `assemble_risk_evidence` 계약으로 검사한다. 체결 ID·주문 연결·개별 체결 시각·수량·금액·최종 수수료와 세금, 현금·NAV·자금 사건·평가 시세·조회 범위가 필요하다.
- 승인된 위험 평가가 없어서 최종 비용을 가져올 수 없던 순환을 제거했다. 정산 원본을 먼저 검사하고, 주문별 비용 확정과 위험 재평가를 같은 SQLite 상태에 저장한다. 기존 사용자 지정 초기금은 공식 초기 자금으로 바꾸지 않는다.
- 부분 매수/매도는 이동평균 원가, 모든 청산으로 수량이 0이 된 한 구간을 연속 손실 1건으로 계산한다. 정산을 다시 받아도 체결 ID별 전량 재계산이라 중복 집계하지 않는다. ID가 같은 정정·삭제·이력 누락은 자동 수정하지 않는다.
- 입출금은 자본 변동, 배당은 배당 수익, 계좌 수수료는 별도 비용으로 구분한다. 비용은 USD 소수 6자리 HALF_EVEN, 대조 허용차는 기존 1센트를 유지한다.
- 손실 중지·복원 중지·냉각 시간·상품 제한은 그대로 적용한다. 비용 대기 중에도 현재 보유/매도가능 수량을 검증한 보호 매도·취소 경로는 유지한다.
- 관측 낙폭은 검산된 스냅샷 사이의 값이다. 미관측 가격이나 장중 최저점을 채우지 않는다.
- 재진입 원가에 청산한 과거 매수의 평균을 재사용하지 않는다. 정산 자료가 있으면 현재 남은 취득원가를 사용한다. 비용 대기 중은 증권사가 보고한 현재 남은 원가+기존 비용 예약을 전략 판단용으로 사용하고 확정 비용이라고 표시하지 않는다. 여러 전략이 동일 종목을 보유해 원가 배분이 불명확하면 추측하지 않는다.

## 실제 계좌 연결에서 남은 외부 조건

**현재 기본 KIS 조회 경로는 최종 비용·개별 체결·체결 기준 현금·전체 자금 사건을 제공하는 검증된 공급기가 없다.** 따라서 이번 구현만 설치해도 체결 후 무인 반복 매매가 자동으로 가능해지는 것은 아니다. 첫 체결 후 필수 자료가 없으면 계속 `COSTS_PENDING`이며 다음 매수는 차단한다. 사용자 초기금이나 주문가능액을 공식 현금/NAV로 복사하지 않는다.

공급기 연결 지점은 `StrategyDemoPort(selection, settlement_source_provider=...)`다. 이 함수는 현재 전체 계좌 관측에 대해 검증된 자료만 반환해야 한다. 인터페이스는 다음과 같다.

```python
def provider(manager, normalized_observation):
    # 검증된 실제 캡처/파서가 없다면 None을 반환한다.
    # 원본 시각, 계좌 연결, 범위/페이지 완전성, 출처/해시를 유지한다.
    return normalized_sources_or_none
```

자료 형식은 기존 `demo_readiness.assemble_risk_evidence`의 `sources` 계약이다. 실제 캡처 연결 `_captured_execution_cash_sources`에 현금·NAV·원본 해시와 `normalized_sources_hash=digest(sources)`가 함께 있어야 한다. 이는 프로그램 내부 공급기 연결 계약이며 사용자 JSON의 `verified=True`나 출처 이름만으로 승인하는 입력 명령은 제공하지 않는다. 원본이 없는 실제 KIS 파서나 가상 API를 추가하지 않았다. 합성 자료는 `replay_only`에서 계산할 수 있으나 운영 주문 근거로 사용할 수 없다.

추가 원본이 확보되면 먼저 실제 필드·통화·비용 확정 시점·취소 행·계좌 연결 계약을 확인한 파서를 공급기로 구현한다. 정상화한 임의 예제를 실제 원본이라고 표현하면 안 된다. 현재 개발 완료 범위는 **정산 소비·검산·위험 재평가·전송 전 대조 코드와 합성 실패 시험**이며, **실제 자료 공급 및 실제 반복 체결 검증은 미완료**다.

## 실행·상태 확인

Windows CMD, 프로젝트 루트에서:

```cmd
python Code\execution_status.py
python Code\main.py --test unit-readiness
python Code\main.py --test all
```

Python 3.12를 사용한다. 여러 Python이 설치된 PC에서는 3.12 실행 파일의 절대 경로를 사용한다.

라즈베리파이의 이번 격리 검사 경로에서:

```sh
cd <보고서 arm-tests-meta.json의 path>
.venv/bin/python Code/execution_status.py
.venv/bin/python Code/main.py --test all
```

상태 명령은 SQLite를 읽기 전용으로 열고 계좌번호·인증·원문 응답을 출력하지 않는다. `process_running`은 Linux의 이 설치 경로 프로세스만 확인하며 Windows에서는 미확인(null)이다. 저장된 `eligible`을 보고 주문을 승인하지 않으며 `new_orders_allowed=false`는 상태 도구의 권한을 뜻한다. 실제 런타임 승인은 최신 전체 계좌 조회 후에만 산출한다.

## 배포·롤백

이번 ARM 검사는 별도 경로·빈 상태·인증 미복사 환경이다. 기존 Pi 운영 코드·계좌·인증·서비스·부팅 설정을 변경하지 않는다. 운영 반영 전 원장 backup API 백업과 코드 백업을 만들고 정상 종료 후 코드만 교체해야 한다. 복원 원장을 자동 재전송 근거로 쓰면 안 된다. 개발 전 파일은 이번 보고서의 `before/`에 보존한다. 롤백 시 운영 중인 SQLite나 Credentials를 덮어쓰지 않는다.
